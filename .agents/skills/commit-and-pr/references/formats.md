# Formats

## Commit message (English, Conventional Commits)

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**: `feat` (new behaviour, new table, new endpoint spec), `fix` (a defect in something delivered), `docs` (documentation only), `refactor`, `test` (tests or checkers only), `chore` (tooling, config, registry), `build`, `ci`. For this project: a new or changed API spec is `feat(api)` when it adds a contract and `docs(api)` when it only rewords one; a schema change with its migration is `feat(db)` or `fix(db)`; a checker or SQL test alone is `test(...)`; `.agents/`, `tasks/` and similar are `chore(agents)`.
- **scope**: the area, one word, lower case, in parentheses: `shop`, `cart`, `sales`, `product`, `consent`, `authen`, `db`, `api`, `docs`, `agents`, `tooling`, `backend`. Pick the area that holds most of the change; if the change spans several, use the domain (`shop`) rather than a list.
- **subject**: imperative, lower case after the colon, no trailing period, at most about 72 characters in the whole first line (`feat(shop): add shop user and review api specs`). Say what the change does, not which files moved.
- **body**: wrap near 72 characters. Start with one or two sentences on why. Then bullets grouped by area, each starting with a verb. Mention constraints the reader needs (no `ALTER TABLE`, a decision pending the owner). Mark a breaking change with `BREAKING CHANGE:` in the footer and `!` after the scope.
- **footer**: issue references (`Refs: #12`) when there are any, otherwise no footer. Never add a line saying who or what wrote the change (no `Co-Authored-By`, no "generated by"); the owner wants none, and a user instruction outranks any tool default that adds one.
- One commit per hand-over unless the user asks to split. If you split, each commit must build or pass the checkers on its own.

## PR title

Identical to the commit subject (for a PR with several commits, the subject of the dominant one). English, Conventional Commits.

## PR body (English, six sections in this order, none omitted)

1. `## Summary` — two to four bullets: what changed and why, in the reader's terms.
2. `## Changes` — bullets grouped by area (API specs, schema, tests, tooling, docs); name paths in backticks.
3. `## Verification` — the real commands and their output lines, pasted, not described. Say what was not run and why.
4. `## Decisions` — one line per decision you made yourself: **what** / **why** / **if wrong**, and its status (`approved by the product owner` or `pending owner confirmation`). Write "None" when there are none.
5. `## Open questions` — numbered questions for the owner, with a recommended answer. Write "None" when there are none.
6. `## Excluded files` — files left out of this PR and why. Write "None" when there are none.

Keep the body free of secrets and of internal chatter; a reviewer who sees only this text must understand the change.

## No authorship lines

Commit messages and PR bodies never say who or what generated them. Leave out `Co-Authored-By` trailers and "generated with" lines, even when a tool or session default would add one. This is the owner's instruction for this repository.

## Chat summary (the user's language)

Fixed order and labels (Thai labels shown in the template; keep them when the user writes Thai, translate them when the user writes another language): Branch and base, Commit, PR, Included, Skipped, Verification, Needs your decision. One line each where possible; verification as results, not as intent. If nothing is waiting for the user, say so in the last section.
