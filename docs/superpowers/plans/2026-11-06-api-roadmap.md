# แผนทำ API ที่เหลือ (roadmap)

วันที่: 2026-11-06 · ผู้เขียน: Josh · สถานะ: ฉบับร่าง รอเจ้าของงานเลือกลำดับและตอบคำถามหัวข้อ 6

แผนนี้เรียงงาน API ที่ยังไม่มีทั้งหมดของ `e-commerce/doc/api/` เป็นชุดงาน (WP) พร้อมลำดับ ความเสี่ยง และคำถามที่ต้องตัดสินก่อนเริ่ม ตัวเลขทั้งหมดมาจากการนับ spec ที่มีอยู่จริง ไม่ใช่การประมาณ

## 1. ตอนนี้อยู่ตรงไหน

มี spec แล้ว 28 เส้น ครอบคลุม:

| โดเมน                                      | เส้นที่มี                   | หมายเหตุ                                                        |
| ------------------------------------------ | ----------------------- | -------------------------------------------------------------- |
| authen                                     | register, login (2 เส้น) | reset-password และ create-new-password ยังเป็น template ว่าง      |
| consent                                    | 5 เส้น                   | ครบวงจร (ยกเว้นตาราง consent type)                              |
| product                                    | 9 เส้น                   | product, category, category attribute (upsert, batch, inquiry) |
| shop                                       | 7 เส้น                   | SKU และ lot, หน้าสินค้า (ผม) และ shop type (คุณงาม)                |
| cart                                       | 3 เส้น                   | upsert, batch, inquiry                                         |
| sales, payment, shipping, campaign, author | **0 เส้น**               |                                                                |

จาก 52 ตาราง มี **31 ตารางที่ยังไม่มี API เขียนข้อมูล**:

| โดเมน    | ตารางที่ยังไม่มี API เขียน                                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| sales    | `t_order`, `t_order_item`                                                                                                                     |
| payment  | `t_payment`                                                                                                                                   |
| shipping | `t_shipping`, `t_shipping_item`, `t_shipping_stop`                                                                                            |
| campaign | `m_campaign`, `m_campaign_budget`, `m_campaign_budget_ledger`, `t_campaign_product`, `t_campaign_shop`, `t_campaign_discount`                 |
| author   | `m_role`, `m_permission`, `m_scope`, `t_permission_scope`, `t_role_permission`, `t_role_permission_scope`, `t_user_role`, `t_user_permission` |
| authen   | `t_user_reset_password`, `t_user_access_token`, `t_user_refresh_token`                                                                        |
| product  | `m_product_type`, `m_product_brand`                                                                                                           |
| consent  | `m_consent_type`                                                                                                                              |
| shop     | `m_shop`, `m_shop_image`, `t_shop_user`, `t_shop_product_review` (อยู่ใน T2–T5 ของคุณงาม)                                                        |
| public   | `t_key` (ยังไม่ทราบว่าใช้ทำอะไร)                                                                                                                   |

ช่องว่างที่สำคัญที่สุดคือสายการซื้อต่อจากตะกร้า (order, payment, shipping) เพราะ cart, lot และหน้าสินค้าที่ทำไว้ยังไม่มีทางปิดการขาย

## 2. ชุดงาน

ขนาด: S = 1 ตารางหรือไม่เกิน 3 เส้นแบบง่าย, M = 2–3 ตาราง หรือมีกฎธุรกิจเยอะ, L = หลายตารางที่มีสถานะและการคำนวณ

| WP  | งาน                    | ตาราง                                                                                      | เส้นที่คาด                                                                                                      | ขนาด | ต้องมีก่อน       |
| --- | ---------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | ---- | ------------- |
| WP1 | สั่งซื้อ (checkout, order) | `t_order`, `t_order_item`                                                                  | preview checkout, สร้างออเดอร์จากตะกร้า, inquiry ของลูกค้า, inquiry ฝั่งร้าน, ยกเลิก                                  | L    | cart ✓, lot ✓ |
| WP2 | ชำระเงิน                 | `t_payment`                                                                                | เริ่มชำระ, รับผลจากผู้ให้บริการ (webhook), inquiry, คืนเงิน                                                            | L    | WP1           |
| WP3 | จัดส่ง                   | `t_shipping`, `t_shipping_item`, `t_shipping_stop`                                         | สร้างการจัดส่งจากรายการสั่งซื้อ, อัปเดตจุดทาง, inquiry, ยืนยันรับของ                                                     | L    | WP1, WP2      |
| WP4 | ยืนยันตัวตนให้ครบ          | `t_user_access_token`, `t_user_refresh_token`, `t_user_reset_password` และตารางโปรไฟล์ที่มีแล้ว | เติม login (บันทึก token), refresh, logout, reset password, create new password, โปรไฟล์และที่อยู่ (upsert, inquiry) | M    | –             |
| WP5 | สิทธิ์ (author)           | 8 ตารางของ `author`                                                                        | role, permission, scope (upsert, inquiry), กำหนดสิทธิ์ให้ role และผู้ใช้, ตรวจสิทธิ์                                    | L    | WP4           |
| WP6 | ตารางหลักที่ยังขาด         | `m_product_type`, `m_product_brand`, `m_consent_type`                                      | อย่างละ 3 เส้น (upsert, batch, inquiry) ใช้ต้นแบบ category                                                       | S    | –             |
| WP7 | แคมเปญและส่วนลด         | 6 ตารางของ `campaign`                                                                      | แคมเปญ (พร้อม budget, สินค้า, ร้าน, ส่วนลดซ้อน), inquiry, ledger, คำนวณส่วนลด                                        | L    | WP1           |
| WP8 | shop ที่เหลือ             | ตาราง shop 4 ตัว                                                                            | T2–T5 ใน hand-off                                                                                            | M    | – (คุณงามทำอยู่)  |

## 3. ลำดับที่แนะนำ

1. **WP6 และ WP8 ทำคู่ขนานก่อน** (ไม่พึ่งใคร ใช้เวลาไม่มาก) WP6 เป็นงานเล็กที่ปลดล็อกการจัดการ type และ brand ของสินค้า WP8 อยู่กับคุณงาม
2. **WP1 (ผม)** ทันทีที่ตัดสินใจคำถามข้อ 1–4 ในหัวข้อ 6 เพราะเป็น critical path ของระบบ
3. **WP4** ทำต่อเนื่อง เพราะทุกเส้นที่มี `authorization` ต้องการ token ที่ออกจาก login และตอนนี้ login ยังไม่บันทึก token ลงตาราง
4. **WP2 แล้ว WP3** ตามหลัง WP1 โดยลำดับนี้เพราะรอบจัดส่งขึ้นกับสถานะชำระเงิน
5. **WP5 และ WP7** เป็นงานรอง ทำหลังสายการซื้อครบ WP7 กระทบการคำนวณราคาใน WP1 จึงควรเว้นช่องไว้ใน WP1 (ดูข้อ 4 ในหัวข้อ 6)

## 4. งานที่แนะนำให้ใครทำ

- **ผม:** WP1 → WP2 → WP3 → WP4 (สายหลัก ที่ต้องตัดสินใจแบบเชื่อมกันหลายโดเมน)
- **คุณงาม:** WP8 (T2–T5) → WP6 → WP5 (ต้นแบบเหมือนงานที่ทำอยู่) → WP7 (หลังผมส่ง WP1 เพื่อให้เห็นจุดที่ส่วนลดเข้ามา)
- ทุกงานของคุณงามผ่านการตรวจของผมก่อนเริ่มงานถัดไป ตามที่ตกลงไว้ในคำสั่ง hand-off

## 5. ความเสี่ยง

- **ออเดอร์เปลี่ยนความหมายของ schema:** WP1 น่าจะต้องเพิ่มหรือแก้คอลัมน์ใน `t_order` และ `t_order_item` (เช่นสถานะ ที่อยู่จัดส่ง ณ เวลาสั่ง) ซึ่งกระทบ WP2, WP3 ควรปิดการออกแบบ schema ของ sales ก่อนเขียน spec ของ payment และ shipping
- **ส่วนต่อกับผู้ให้บริการชำระเงิน:** มีเอกสาร `e-commerce/doc/external-api/stripe` อยู่แล้ว WP2 ต้องอ่านและยึดตามนั้น ถ้าไม่ใช้ Stripe ต้องรู้ก่อนเริ่ม
- **การตัดสต็อกพร้อมกัน:** การตัดจำนวนใน lot ตอนสั่งซื้อมีเรื่องแข่งกัน (race) ซึ่งเป็นเรื่องการ implement แต่ spec ต้องกำหนดกติกา (ตัดตอนสร้างออเดอร์ หรือตอนจ่ายเงิน) ให้ชัดเพื่อไม่ให้ผู้ implement ต้องเดา
- **ขนาดงาน:** WP1, WP2, WP3 แต่ละชุดใหญ่กว่างาน cart หลายเท่า ควรแบ่งส่งทีละเส้นและให้ตรวจก่อนไปเส้นถัดไป
- **`public.t_key`:** ไม่มีใครรู้ว่าใช้ทำอะไร ถ้าไม่เกี่ยวกับ API ควรบันทึกว่าไม่อยู่ในขอบเขต

## 6. คำถามที่ต้องตัดสินก่อนเริ่ม (เรียงตามความสำคัญ)

1. **ตัดสต็อกเมื่อไหร่:** ตัดจาก lot ตอนสร้างออเดอร์ (เร็ว กันขายเกิน แต่ต้องมีเวลาหมดอายุของออเดอร์ที่ไม่จ่าย) หรือตอนชำระเงินสำเร็จ (ง่ายกว่า แต่ขายเกินได้) ข้อนี้กำหนดสถานะ `WAIT_PAYMENT` และการยกเลิก
2. **ตะกร้าที่มีหลายร้าน:** `t_order` มี `shop_id` อยู่แล้ว ผมเสนอให้ checkout หนึ่งครั้งสร้างหนึ่งออเดอร์ต่อร้าน และจ่ายเงินรวมหรือแยกตามร้านต้องตัดสินใจ (ผลต่อ `t_payment` ที่อ้าง `order_id`)
3. **ราคาในออเดอร์:** ล็อกราคาจาก lot ที่เปิดขาย ณ ตอนสร้างออเดอร์ (เสนอ) และ `price` ใน `t_order_item` คือราคานั้น
4. **ส่วนลด ภาษี ค่าส่ง:** คำนวณที่ checkout หรือไม่ และสูตรคืออะไร ถ้าส่วนลดมาจากแคมเปญ (WP7) ควรเว้นจุดเสียบไว้ใน WP1 หรือทำ WP7 ก่อน
5. **ที่อยู่จัดส่ง:** `t_order.address_id` ชี้ไปที่อยู่ของผู้ใช้ ถ้าผู้ใช้แก้ที่อยู่ทีหลัง ออเดอร์เก่าจะเปลี่ยนตาม ต้องการเก็บสำเนา ณ เวลาสั่งหรือไม่
6. **Payment provider:** ใช้ Stripe ตามเอกสาร external-api หรือไม่ และมีวิธีชำระอื่นไหม (โอน, เก็บปลายทาง)
7. **สิทธิ์:** ตอนนี้ทุกเส้นฝั่งผู้ดูแลมีแค่ `authorization` ยังไม่มีการตรวจสิทธิ์รายเส้น (ใครเรียก upsert สินค้าได้) ต้องการให้กำหนดใน WP5 แล้วย้อนกลับไปใส่ใน spec เดิมทุกเส้นหรือไม่
8. **`public.t_key`:** ใช้ทำอะไร และต้องมี API ไหม

## 7. วิธีทำแต่ละ WP (เหมือนที่ใช้มาตลอด)

1. เขียนรายการกฎที่ต้องตัดสินใจ ตอบคำถามที่เป็นของเจ้าของงานก่อน
2. แก้ schema ที่ `CREATE TABLE` โดยตรง (ไม่ใช้ `ALTER TABLE`) พร้อมแบบทดสอบ SQL ที่ล้มก่อนแก้
3. คัดลอก spec ต้นแบบแล้วเขียน spec ทุกเส้นของชุดตามข้อตกลง (รหัส HTTP, bizCode, batch, inquiry, SQL)
4. เพิ่มตัวตรวจของชุดใน `check_docs.py` แล้วทดสอบตัวตรวจด้วยความผิดพลาดจงใจ
5. รันตัวตรวจทั้งหมด, `audit_all.py` (ต้อง 0 ข้อพบ), `run_db_tests.sh` และเปิดดู ER diagram จริง
6. สรุปการตัดสินใจ (ตัดสินอะไร เพราะอะไร ถ้าผิดเสียอะไร) ให้เจ้าของงานตรวจ ไม่ commit จนกว่าจะอนุมัติ
