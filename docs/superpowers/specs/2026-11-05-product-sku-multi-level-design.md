# Product SKU แบบหลาย level (Multi-level SKU)

วันที่: 2026-11-05 · สถานะ: ฉบับอนุมัติแล้ว (มีการตัดสินระหว่างลงมือทำ R6-R12 รอเจ้าของงานตรวจ)

## ทำไมถึงต้องทำ

ตอนนี้ `product.m_product_sku` มีแค่ `product_id`, `name`, `description` ไม่มีโครงสร้างตัวเลือก (ตัวเลือกคือสิ่งที่ลูกค้าเลือก เช่น ลาย ไซส์ สี) สินค้าอย่างเสื้อหรือเส้นที่มีหลายลาย หลายไซส์ หลายสี จึงนิยามไม่ได้ว่า SKU แต่ละตัวมาจากตัวเลือกไหน และหน้าสินค้าก็เปลี่ยนรูป ราคา สถานะสต็อกตามที่ลูกค้าเลือกไม่ได้

## เป้าหมาย

- สินค้า 1 ตัวนิยาม "level" ของตัวเลือกได้ ตอนนี้จำกัดไม่เกิน 3 level เช่น ลาย → ไซส์ → สี
- โครงสร้างข้อมูลไม่ฝังเลข 3 ไว้ จะรองรับ 4 level ได้ในอนาคตโดยแก้ค่า config ไม่ต้องแก้ตาราง
- ชื่อ level และค่าในแต่ละ level ร้านตั้งเองต่อสินค้า
- ระบบสร้าง SKU ให้ครบทุกคู่ของค่าโดยอัตโนมัติ (เช่น 2 ลาย × 3 ไซส์ × 4 สี = 24 SKU)
- ร้านส่ง level, ค่า และรูปมาพร้อมกับ product upsert ในคำขอเดียว
- รูปผูกกับ "ค่า" ของ level ใดก็ได้ และเมื่อมีหลายค่าที่มีรูปพร้อมกัน ใช้รูปของ level ล่างสุดที่มีรูป
- ตารางที่อ้าง `m_product_sku.id` อยู่แล้ว ได้แก่ `shop.t_shop_product_sku`, `cart.t_cart`, `order.t_order_item` ใช้ต่อได้โดยไม่ต้องเปลี่ยนจากฝั่ง product (ฝั่งร้านและออเดอร์อาจเพิ่มการอ้างถึง lot ในโปรเจกต์ 2)

## ไม่ใช่เป้าหมาย

- ราคา สต็อก ต้นทุน และ lot ไม่เพิ่มที่ฝั่งสินค้า ปัจจุบันอยู่ที่ `shop.t_shop_product_sku` (ค่าเดียวต่อ SKU) ซึ่งไม่พอสำหรับหลาย lot จึงต้องปรับโครงสร้างฝั่งร้านในโปรเจกต์ 2 เอกสารนี้ไม่แตะส่วนนั้น
- เอกสารนี้ไม่รวม API ฝั่งร้านสำหรับตั้งราคา/สต็อกต่อ SKU และ API ที่ให้หน้าสินค้าได้ราคา ช่วงราคา และสถานะหมดสต็อก สองส่วนนี้อยู่ในขอบเขตของงานรวม แต่แยกเป็นโปรเจกต์ที่ทำต่อจากนี้ (ดูหัวข้อ "ลำดับโปรเจกต์")
- ไม่ทำการปิดบาง combination (ทุกคู่ถูกสร้างเสมอ)
- ไม่ทำ SKU แบบตัวเลือกที่ขึ้นกับค่าของ level บน (ไม่ใช่โครงสร้างต้นไม้) ทุก level ใช้ชุดค่าเดียวกันกับทุกค่าของ level บน
- ไม่ทำ migration ข้อมูลเก่า (ยังไม่มีข้อมูลจริง)

## สิ่งที่ไม่ยอมให้เกิด

- SKU ซ้ำ combination ในสินค้าเดียวกัน
- ลบ SKU ที่ถูกร้าน ตะกร้า หรือออเดอร์อ้างอิงอยู่แบบถาวร (ใช้ soft delete เสมอ)
- ตัวเลขสูงสุด 3 level ฝังอยู่ใน schema

## ข้อจำกัด

- ใช้ PostgreSQL ตามเดิม ตารางใหม่ทุกตัวใช้คอลัมน์มาตรฐานของระบบ (`id`, `created_by`, `created_at`, `updated_by`, `updated_at`, `row_status`)
- ใช้ soft delete ผ่าน `row_status` เหมือนทุกตาราง
- รูปแบบ API เดิม: upsert ครอบ insert/update/delete ด้วย `rowStatus: "DELETED"`
- งานนี้เป็นงานเอกสาร (migration, schema doc, ER diagram, spec) ไม่ใช่โค้ดแอปพลิเคชัน

## สิ่งที่เจ้าของงานตัดสินใจแล้ว

1. ราคา ต้นทุน และจำนวนสต็อก ตั้งที่ระดับ lot ใต้ SKU ระดับสุดท้ายเท่านั้น (แต่ละ lot ต้นทุนและราคาขายไม่เท่ากัน) ร้านเปิดขายทีละ lot ต่อ SKU และลูกค้าเห็นและซื้อในราคาของ lot ที่เปิดขายอยู่
2. ชื่อ level ร้านตั้งเองต่อสินค้า (ไม่ผูกกับ category และไม่ใช่รายการกลาง)
3. ตัวเลือกในแต่ละ level ผสมอิสระทุกคู่ (ไม่เป็นต้นไม้)
4. เมื่อลูกค้าเลือกตัวเลือก ต้องเปลี่ยนตาม 3 อย่าง: รูปสินค้า, ราคา, สถานะสต็อก
5. รูปผูกกับค่าของ level ไหนก็ได้ และใช้รูปของ level ล่างสุดที่มีรูป
6. ส่ง level, ค่า และรูป พร้อมกับ product upsert (ไม่แยกเป็นเส้นของตัวเอง)
7. SKU ถูกถอดออกจาก spec product รอบก่อน (รอคุยรอบนี้) ส่วน `images` และ `attributes` ยังอยู่ตามเดิม
8. ขอบเขตงานรวมครอบคลุมทั้ง API ฝั่งร้านที่ตั้งราคา/สต็อกต่อ SKU และ API ที่ให้หน้าสินค้าได้ราคา ช่วงราคา และสถานะสต็อกต่อ SKU โดยแยกคุยเป็นโปรเจกต์ต่อจากเอกสารนี้

## ภาพรวมการออกแบบ

### โครงสร้างข้อมูล

ตารางใหม่ 3 ตาราง และแก้ 2 ตารางเดิม ทั้งหมดอยู่ใน schema `product`

| ตาราง | ทำอะไร | คอลัมน์สำคัญ |
|---|---|---|
| `m_product_option` (ใหม่) | level ของสินค้า | `product_id`, `name`, `level_no` (เริ่ม 1) |
| `m_product_option_value` (ใหม่) | ค่าใน level | `option_id`, `value`, `sort_order` |
| `m_product_sku_option_value` (ใหม่) | บอกว่า SKU แต่ละตัวประกอบด้วยค่าอะไร | `sku_id`, `option_value_id` |
| `m_product_sku` (แก้) | SKU ที่ซื้อได้จริง | เพิ่ม `combination_key` |
| `m_product_image` (แก้) | รูป | เพิ่ม `option_value_id` (nullable) |

- `m_product_option`: unique `(product_id, level_no)` และ unique `(product_id, name)` ตัวเลข `level_no` ต้องต่อเนื่องตั้งแต่ 1 ขึ้นไป
- `m_product_option_value`: unique `(option_id, value)`
- `m_product_sku_option_value`: unique `(sku_id, option_value_id)` และ SKU หนึ่งตัวมีค่าครบทุก level ของสินค้า level ละ 1 ค่า (ตรวจฝั่งแอป)
- `m_product_sku.combination_key`: สตริงที่ประกอบจาก id ของค่าตามลำดับ level ใช้ unique `(product_id, combination_key)` เพื่อกัน SKU ซ้ำ combination ระดับฐานข้อมูล
- `m_product_image.option_value_id`: ว่าง = รูปรวมของสินค้า, มีค่า = รูปของค่านั้น ค่าหนึ่งมีได้หลายรูป
- `m_product_sku.name` สร้างอัตโนมัติจากชื่อค่าต่อกัน เช่น `ลาย A / M / แดง`

### กฎการสร้างและแก้ SKU

- สินค้าที่ไม่มี level จะมี SKU เริ่มต้น 1 ตัวที่ไม่มีค่าใน level ใดเลย (`combination_key` เป็นค่าว่าง) เพราะราคาของร้านอยู่ใต้ SKU (`shop.t_shop_product_sku` ซึ่งบังคับ `sku_id` และ lot ที่จะเพิ่มในโปรเจกต์ 2) ถ้าไม่มี SKU สินค้านั้นจะไม่มีที่เก็บราคา (`shop.t_shop_product` มีแค่ `quantity`) ส่วน `sku_id` ที่เป็น optional ใน `t_cart` และ `t_order_item` คงไว้ตามเดิม
- เมื่อสินค้าเริ่มมี level แรก SKU เริ่มต้นที่ยังไม่ถูกใช้งานจะถูกปิด และสร้าง SKU ตามค่าใน level ใหม่ ถ้า SKU เริ่มต้นถูกใช้งานแล้ว ตอบ 409 ตามกฎการแก้ level ด้านล่าง
- SKU ที่สร้าง = ผลคูณคาร์ทีเซียนของค่าที่ `ACTIVE` ในทุก level
- เพิ่มค่าใหม่ในสินค้าที่มี SKU อยู่แล้ว: สร้าง SKU ใหม่ให้ครบทุกคู่ที่เกี่ยวข้อง
- ลบหรือปิดค่า (`DELETED`, `INACTIVE`): ปิด SKU ทุกตัวที่ใช้ค่านั้นแบบ soft ด้วย `row_status` เดียวกัน ถ้าเปิดค่ากลับเป็น `ACTIVE` ให้เปิด SKU ที่เกี่ยวข้องกลับ
- เพิ่มหรือลดจำนวน level ของสินค้าที่มี SKU ถูกใช้งานอยู่แล้ว (ถูกร้าน ตะกร้า หรือออเดอร์อ้าง): ไม่อนุญาต ตอบ 409 ถ้ายังไม่มีใครใช้ SKU เลย อนุญาต และให้ปิด SKU เดิมแล้วสร้างใหม่
- จำนวน level สูงสุดอ่านจาก config ของแอป ค่าเริ่มต้น 3

### รูปแบบ API (แก้ product upsert, product upsert batch และ product inquiry)

- body ของ upsert เพิ่ม `options[]` แต่ละ level มี `id` (optional), `name`, `rowStatus` (optional) และ `values[]` ที่มี `id` (optional), `value`, `rowStatus` (optional) กับ `images[]` ของค่านั้น (ฟิลด์เหมือน `images` ที่มีอยู่เดิม) การลำดับของ `options[]` กำหนด `level_no`
- ส่ง `options` มา = แทนที่ตามกฎ id (ไม่ส่ง id คือเพิ่ม ส่ง id คือแก้ `rowStatus: "DELETED"` คือลบ) ไม่ส่ง `options` = คงของเดิม
- `images[]` ระดับสินค้าที่มีอยู่เดิมยังอยู่ เป็นรูปรวมของสินค้า
- inquiry คืน `options[]` (level และค่า พร้อมรูปของค่า) และ `skus[]` (`skuId`, `name`, `optionValueIds` ตามลำดับ level, สถานะ) ไม่คืนราคาหรือสต็อก
- response ของ upsert ยังคืน `productId` ตามเดิม

### การแสดงผลรูปบนหน้าสินค้า (กติกา ไม่ใช่ API)

เมื่อลูกค้าเลือกค่าในหลาย level ใช้รูปของค่าใน level ล่างสุดที่มีรูป ถ้าไม่มีค่าไหนที่เลือกมีรูป ใช้รูปรวมของสินค้า

## สิ่งที่ผมเลือกเอง (เจ้าของงานตรวจดูได้)

- ใช้ตารางเชื่อม `m_product_sku_option_value` แทนการเพิ่มคอลัมน์ `option_1/2/3` ใน `m_product_sku` เพื่อให้ไม่ฝังเลข 3
- เพิ่ม `combination_key` เพื่อกัน SKU ซ้ำที่ระดับฐานข้อมูล
- ผูกรูปด้วยการเพิ่ม `option_value_id` ใน `m_product_image` แทนการสร้างตารางรูปใหม่
- ชื่อ SKU สร้างจากชื่อค่าคั่นด้วย ` / `
- เพดานจำนวน SKU ต่อสินค้า อ่านจาก config ค่าเริ่มต้น 500 ถ้าเกินตอบ 400
- กฎการแก้ level เมื่อ SKU ถูกใช้งานแล้ว (ตอบ 409)
- `options` ที่ส่งมาซ้ำ `name` หรือ `value` ซ้ำใน level เดียวกัน ตอบ 400
- สิทธิ์เรียก API เหมือน product upsert เดิม (ต้องมี `authorization`)
- สินค้าที่ไม่มี level มี SKU เริ่มต้น 1 ตัว (แก้จากที่ผมเดาไว้ตอนแรกว่าไม่มี SKU เลย เพราะราคาของร้านต้องมี `sku_id`)

## ที่เหลือให้ผู้สร้างตัดสินใจ

- ชื่อคอลัมน์และชนิดข้อมูลจริง (เช่น `level_no` เป็น `SMALLINT`)
- รูปแบบการประกอบ `combination_key`
- ลำดับการแสดงค่าในแต่ละ level (`sort_order`)
- ข้อความ error และ `bizCode` ใหม่ที่ต่อจากชุดเดิม

## ลำดับโปรเจกต์

งานรวมแบ่งเป็น 3 โปรเจกต์ ทำตามลำดับนี้ และแต่ละส่วนจะมีการคุยและเอกสารออกแบบของตัวเอง

1. **ฝั่ง product (เอกสารนี้):** level, ค่า, รูป และการสร้าง SKU ผ่าน product upsert/batch/inquiry
2. **ฝั่งร้าน ตั้งราคา/สต็อกแบบ lot:** แต่ละ SKU มีหลาย lot แต่ละ lot มีต้นทุน ราคาขาย และจำนวนของตัวเอง ร้านเปิดขายทีละ lot ต่อ SKU รวมถึงกรณีที่มี SKU ใหม่เกิดขึ้นแล้วร้านต้องเพิ่มเข้าร้าน และออเดอร์ต้องจำได้ว่าขายจาก lot ไหน (เพื่อคิดกำไรจากต้นทุนของ lot นั้น) คำถามที่ต้องคุยในโปรเจกต์นี้: เมื่อ lot ที่เปิดขายหมด ร้านเปิด lot ถัดไปเอง หรือระบบเปิดให้อัตโนมัติ
3. **หน้าสินค้า (storefront):** inquiry ที่คืน level, ค่า, รูป, ราคาต่อ SKU (ราคาของ lot ที่เปิดขายอยู่), ช่วงราคาเมื่อเลือกยังไม่ครบ และสถานะสต็อก (รวมการปิดตัวเลือกที่หมด)

## การตัดสินระหว่างลงมือทำ (รอเจ้าของงานตรวจ)

- R6 options เป็นนิยามครบทั้งชุด (ตัวที่ไม่อยู่ในรายการถูกลบแบบ soft และปิด SKU, array ว่างลบทุก level)
- R7 DELETED เปิดกลับไม่ได้ (เพิ่มเป็นค่าใหม่), INACTIVE/LOCKED/ARCHIVED เปิดกลับได้และเปิด SKU กลับเมื่อทุกค่าใน SKU เป็น ACTIVE, option รับเฉพาะ ACTIVE/DELETED
- R8 เพดาน 500 SKU คำนวณจากคำขอก่อนเขียน ทั้งคำขอเป็น transaction เดียว, การสลับลำดับ level นับเป็นการแก้ level (409 เมื่อ SKU ถูกใช้)
- R9 inquiry คืน option ACTIVE เท่านั้น และค่า/SKU ที่ไม่ใช่ DELETED พร้อม rowStatus
- R10 ลำดับการประมวลผลและการเปลี่ยนชื่อสองขั้น
- R11 ชื่อ SKU ตามการเปลี่ยนชื่อค่า/ชื่อสินค้า
- R12 level_no ของ option ที่ลบคงเดิม, sort_order เริ่มที่ 1, เพดานนับเฉพาะ ACTIVE
