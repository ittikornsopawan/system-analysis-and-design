## เป้าหมาย

- แพลตฟอร์มสร้างแคมเปญ: ช่วงเวลา ร้านและสินค้าที่เข้าร่วม ส่วนลด และงบ
- ส่วนลดคำนวณฝั่งเซิร์ฟเวอร์ที่ checkout preview และตอนสร้างออเดอร์ ลงที่ `t_order_item.discount` และ `t_order.total_discount` (ที่ตอนนี้เป็น 0.00 ตาม R41)
- งบถูกกันตอนสร้างออเดอร์ คืนเมื่อออเดอร์ถูกยกเลิก (รวมหมดเวลา) หรือคืนเงิน และงบห้ามติดลบแม้สั่งพร้อมกัน
- แพลตฟอร์มดูแคมเปญ งบ และ ledger ร้านที่เข้าร่วมดูแคมเปญของตัวเอง

## ไม่ใช่เป้าหมาย

- ส่วนลดค่าส่ง ภาษี โค้ดคูปอง ส่วนลดตามยอดขั้นต่ำหรือตามผู้ใช้ (schema ไม่มีเงื่อนไขเหล่านี้)
- แคมเปญที่ร้านสร้างเองและงบของร้าน (ดู C1)
- แสดงราคาลดบนหน้าสินค้าและตะกร้า ส่วนลดเห็นที่ checkout และในออเดอร์เท่านั้น
- ตัวตั้งเวลา (job) ใด ๆ
- การแก้ spec หรือ schema ที่ส่งมอบแล้ว (sales, payment, shop, product) เขียนเป็นข้อเสนอท้ายเอกสาร ห้ามแก้เอง

## 1. ข้อเท็จจริงที่อ้างอิง (ตรวจกับไฟล์ใน `origin/main` ที่ `738f215`)

ไม่มีบริการภายนอกในงานนี้ ทุกข้อด้านล่างมาจากไฟล์ใน repo

| ข้อเท็จจริง | ที่มา | ผลต่อการออกแบบ |
|---|---|---|
| `m_campaign` มี `name`, `description`, `start_at`, `end_at` ไม่มีเจ้าของ ไม่มี `CHECK (end_at > start_at)` และชื่อไม่ unique | migration 09 | ต้องเพิ่ม check และ unique ของชื่อ (C11) |
| `m_campaign_budget` มี `budget` ไม่มียอดคงเหลือ ไม่ unique ต่อแคมเปญ | migration 09 | ไม่มีแถวเดียวให้ทำ `UPDATE ... WHERE remaining >= n` ต้องเพิ่ม `remaining` (C9, C11) |
| `m_campaign_budget_ledger` มี `reference JSONB`, `usage >= 0`, `remaining >= 0` ไม่มีชนิดรายการและไม่มี `order_id` | migration 09 | คืนงบเป็น `usage` ติดลบไม่ได้ ต้องมี `entry_type` และ `order_id` (C11) |
| `t_campaign_product` มี `product_category_id` และ `product_id` ทั้งคู่ว่างได้ ไม่มี check และไม่มี unique | migration 09 | ต้องบังคับว่าตั้งค่าได้อย่างเดียว (C11) ตารางผูกกับสินค้าและหมวดเท่านั้น **ไม่ผูก lot** (ที่ handoff เขียนถึง lot ไม่ตรงกับ schema) |
| `t_campaign_discount` มี `discount_type` (`PERCENTAGE`, `FIXED_AMOUNT`) และ `discount_value >= 0` ไม่มีเพดาน 100 สำหรับเปอร์เซ็นต์ ไม่มีเงื่อนไขขั้นต่ำ | migration 09 | ไม่มีเงื่อนไขให้เลือกระหว่างหลายแถว (C3) |
| `t_order.total_amount = total_price - total_discount + total_tax + total_shipping` บังคับด้วย `ck_t_order_total_amount_sum` | migration 06 | เสียบส่วนลดได้โดยไม่แก้ schema ของ sales (R41) |
| `t_order_item.total_price = price × quantity` (ไม่หักส่วนลด) `discount` เก็บแยก `gross_profit >= 0` ส่วน `shop_profit`, `platform_profit` ไม่มี check | migration 06 | ราคาในรายการไม่เปลี่ยน ส่วนลดเก็บที่ `discount` (C4) เพดานส่วนลดต้องไม่ทำให้ `gross_profit` ติดลบ (C5) |
| `gross_profit = shop_profit + platform_profit` ในตัวอย่างของ spec (158.00 = 110.60 + 47.40) lot มี `gross_margin`, `share_margin`, `platform_margin` | `sales/02`, `shop/01` | สูตรกำไรหลังลด (C6) |
| ราคาและสต็อกล็อกตอนสร้างออเดอร์ สต็อกตัดด้วย `UPDATE ... WHERE quantity >= n` ออเดอร์เกิดเป็น `WAIT_PAYMENT` ถือสต็อกถึง `expires_at` | R38, R40, R45, `sales/02` | งบทำแบบเดียวกัน (C7, C9) |
| สต็อกกลับเข้า lot ที่ 3 จุด: ยกเลิกออเดอร์และตัวตั้งเวลา (`sales/05`), คืนเงินเต็มจำนวน (`payment/05`), webhook `charge.refunded` ที่ payment `COMPLETED` → `REFUNDED` (`payment/02`) การคืนเงินที่เข้าหลังออเดอร์ถูกยกเลิกไปแล้ว (R57) ไม่คืนสต็อกซ้ำ | `sales/05`, `payment/05`, `payment/02` | งบต้องคืนที่ 3 จุดเดียวกัน และไม่คืนกรณี R57 (C7) |
| ยอดชำระ `amount = totalPrice - totalDiscount + totalTax + shippingFee` และต่ำสุด 10.00 บาท (config) | `payment/01` (R54, R65, R67) | ส่วนลดรวมอยู่ในยอดชำระแล้วโดยไม่ต้องแก้ payment และยอดรวมค่าส่งจึงไม่ต่ำกว่าขั้นต่ำ (C14) |
| ล็อกแถว `sales.t_order` ก่อนเสมอ แล้วจึงแก้ตารางอื่น | R72 | งบอยู่หลังออเดอร์และ lot ในลำดับล็อก (C9) |

| ลบร้านถูกห้ามเมื่อมีสินค้าหรือออเดอร์ (409 E10006) ไม่ตรวจแคมเปญ ลบสินค้าและหมวดมีกติกาของตัวเอง | `shop/08–09`, `product/01–06` | ข้อเสนอแก้ตามหัวข้อ 4 (C13) |
| `product.m_product.category_id` ผูกสินค้ากับหมวด และหมวดมี `parent_id` | migration 03 | แคมเปญตามหมวด: เลือกหมวดเดียว ไม่รวมหมวดลูก (C2) |

## 2. Endpoint (รอบ 2)

โฟลเดอร์ `e-commerce/doc/api/campaign/`

| โฟลเดอร์ | Endpoint | ผู้เรียก | สิทธิ์ |
|---|---|---|---|
| `01-upsert-campaign` | `POST v1/campaign/upsert` | แพลตฟอร์ม | `PLATFORM_ADMIN` เท่านั้น (ไม่ใช่ 403 E10009) |
| `02-inquiry-campaign` | `GET v1/campaign` | แพลตฟอร์ม และร้านที่เข้าร่วม | `PLATFORM_ADMIN` เห็นทุกแคมเปญพร้อมงบ สมาชิก ACTIVE ของร้านที่ส่ง `shopId` เห็นแคมเปญที่มีผลกับร้าน คือแคมเปญที่ร้านอยู่ใน `t_campaign_shop` หรือไม่มีแถวร้านเลย (C2) ไม่เห็นงบ ยอดคงเหลือ และ ledger |
| `03-inquiry-campaign-ledger` | `GET v1/campaign/ledger` | แพลตฟอร์ม | `PLATFORM_ADMIN` เท่านั้น |

- เส้น 01 เป็น upsert เดี่ยวของแคมเปญ ลูกซ้อนในคำขอ: `budget` (หนึ่งก้อน), `discount` (หนึ่งแถว), `shops[]`, `products[]` ตามกติกาลูกซ้อนของโปรเจกต์ (ไม่ส่ง `id` = เพิ่ม, ส่ง `id` = แก้, `rowStatus` `DELETED` = ลบ, ที่ไม่ได้ส่ง = คงไว้) ใช้ต้นแบบ `shop/08` (รูปซ้อน) และ `shop/11` (สิทธิ์)
- ไม่มี batch: แคมเปญสร้างโดยผู้ดูแลแพลตฟอร์มไม่กี่คนทีละใบ และแต่ละใบมีลูกซ้อนหลายชนิด ถ้าผิด (ต้องการนำเข้าหลายใบ): เพิ่มเส้น batch ตามแบบ `shop/09`
- ledger ไม่มีเส้นเขียน: ระบบเขียนเองตอนกันและคืนงบ (C9) มีเฉพาะ inquiry
- การคำนวณส่วนลดไม่มี endpoint ของตัวเอง อยู่ใน `sales/01` และ `sales/02` (ข้อเสนอแก้ E1, E2)
- รหัส error ใช้ชุดเดิม ไม่สร้างรหัสใหม่ (C15)

## 3. การเปลี่ยน schema ที่เสนอ (แก้ที่ `CREATE TABLE` ของ migration 09 ไม่ใช้ `ALTER TABLE`)

ทั้ง 6 ตารางยังไม่มี spec และยังไม่ส่งมอบ จึงแก้ได้ (มีแบบทดสอบ `09-campaign.test.sql` เดิมที่ต้องคงผ่าน)

| ตาราง | เปลี่ยน |
|---|---|
| `m_campaign` | `CONSTRAINT ck_m_campaign_period CHECK (end_at > start_at)` · partial unique `uq_m_campaign_name` บน `(name) WHERE row_status <> 'DELETED'` |
| `m_campaign_budget` | เพิ่ม `remaining NUMERIC(16, 2) NOT NULL CHECK (remaining >= 0)` และ `CONSTRAINT ck_m_campaign_budget_remaining CHECK (remaining <= budget)` · partial unique `uq_m_campaign_budget_campaign_id` บน `(campaign_id) WHERE row_status <> 'DELETED'` (หนึ่งแคมเปญหนึ่งงบที่ใช้อยู่ C10) |
| `m_campaign_budget_ledger` | เพิ่ม `entry_type VARCHAR(16) NOT NULL CHECK (entry_type IN ('RESERVE', 'RELEASE'))` และ `order_id UUID NOT NULL REFERENCES sales.t_order (id) ON DELETE RESTRICT` · `UNIQUE (campaign_budget_id, order_id, entry_type)` (ledger เพิ่มอย่างเดียว ไม่ลบแบบ soft จึงใช้ unique ธรรมดาตามแนว R62) · `usage` คือ n (บวกเสมอ) ทั้ง `RESERVE` และ `RELEASE` ส่วน `remaining` คือยอดคงเหลือของงบหลังรายการนั้น · คง `reference JSONB` ไว้เก็บรายละเอียดต่อรายการ `[{"orderItemId": ..., "discount": ...}]` |
| `t_campaign_product` | `CONSTRAINT ck_t_campaign_product_target CHECK ((product_category_id IS NULL) <> (product_id IS NULL))` · partial unique `(campaign_id, product_id) WHERE product_id IS NOT NULL AND row_status <> 'DELETED'` และ `(campaign_id, product_category_id) WHERE product_category_id IS NOT NULL AND row_status <> 'DELETED'` |
| `t_campaign_shop` | partial unique `(campaign_id, shop_id) WHERE row_status <> 'DELETED'` |
| `t_campaign_discount` | `discount_value > 0` แทน `>= 0` · `CONSTRAINT ck_t_campaign_discount_percentage CHECK (discount_type <> 'PERCENTAGE' OR discount_value <= 100)` · partial unique `(campaign_id) WHERE row_status <> 'DELETED'` (C3) |

จำนวนคอลัมน์ใน README: `m_campaign_budget` 8 → 9, `m_campaign_budget_ledger` 11 → 13 ตัวอื่นเท่าเดิม ไม่มี FK ใหม่นอกจาก `ledger.order_id` (ชี้ `sales` ซึ่ง migration 06 สร้างก่อน 09 จึงไม่เป็น FK วงหรือ FK ไปข้างหน้า)

**ไม่เพิ่ม `campaign_id` ใน `sales.t_order_item`:** จะเป็น FK จาก migration 06 ไปหา 09 ซึ่งยังไม่มีตอนนั้น และเป็นการแก้ตารางที่ส่งมอบแล้ว การดูว่ารายการใดได้ส่วนลดจากแคมเปญใด อ่านจาก `reference` ของ ledger แทน

## การตัดสินใจ

ป้าย: **[ขอเจ้าของงานตอบ]** เป็นเรื่องธุรกิจ ผมเสนอคำตอบไว้และจะไม่ถือว่าเป็นจริงจนกว่าเจ้าของงานตอบ · **[Tommy ตัดสิน]** เรื่องเล็กหรือเทคนิค ผมเลือกเองและรอตรวจ

- **C1 [ขอเจ้าของงานตอบ] ใครสร้างแคมเปญ: `PLATFORM_ADMIN` เท่านั้น** สร้าง แก้ ลบ archive สมาชิก ACTIVE ของร้านดูได้เฉพาะแคมเปญที่ร้านตัวเองอยู่ใน `t_campaign_shop` และเข้าร่วมเมื่อแพลตฟอร์มเพิ่มร้านเท่านั้น เหตุผล: งบเป็นเงินของแพลตฟอร์ม (C6) schema ไม่มีคอลัมน์เจ้าของ และแคมเปญของร้านเองต้องมีงบของร้านและกติกาแยก ถ้าผิด (ร้านสร้างเองได้): เพิ่ม `shop_id` เจ้าของใน `m_campaign` (null = ของแพลตฟอร์ม) แยกสิทธิ์ของแคมเปญร้านกับของแพลตฟอร์ม และตัดสินว่าใครออกงบ
- **C2 [ขอเจ้าของงานตอบ] เมื่อไรที่แคมเปญมีผลกับรายการ** ต้องครบทุกข้อ: (1) แคมเปญ `row_status = 'ACTIVE'` (2) `start_at <= เวลาที่สร้างออเดอร์ < end_at` (UTC) (3) ร้านของรายการอยู่ใน `t_campaign_shop` ที่ ACTIVE และแคมเปญที่ไม่มีแถวร้านเลย = ใช้กับทุกร้าน (4) สินค้าของรายการตรงกับ `t_campaign_product` ที่ ACTIVE ได้ทั้งแบบ `product_id` ตรง หรือ `product_category_id` ตรงกับ `m_product.category_id` (หมวดเดียว ไม่รวมหมวดลูก) และแคมเปญที่ไม่มีแถวสินค้าเลย = ใช้กับทุกสินค้า เหตุผล: ไม่ต้องมีคอลัมน์ scope เพิ่ม ความเสี่ยงคือแคมเปญที่ลืมใส่ร้านหรือสินค้าจะมีผลกับทุกอย่าง จึงมีงบเป็นเพดานป้องกัน ถ้าผิด (ว่าง = ไม่มีผลกับใคร): กลับเงื่อนไขข้อ 3 และ 4 ไม่แก้ schema
- **C3 [ขอเจ้าของงานตอบ] ไม่ซ้อนส่วนลดข้ามแคมเปญ และหนึ่งแคมเปญมีส่วนลดแถวเดียว** รายการหนึ่งได้ส่วนลดจากแคมเปญเดียว คือแคมเปญที่ให้ส่วนลดมากที่สุดของรายการนั้นหลังใช้เพดาน C5 เสมอกันเลือก `campaign_id` ที่น้อยกว่า เหตุผล: ส่วนลดซ้อนทำให้คาดการณ์ยอดและกำไรยาก และ schema ไม่มีเงื่อนไข (ยอดขั้นต่ำ ลำดับ) ที่ใช้เลือกว่าแถวส่วนลดแถวไหนใช้เมื่อมีหลายแถว ไม่มี fallback: ถ้างบของแคมเปญอันดับแรกไม่พอ ไม่ย้ายไปใช้แคมเปญอันดับสองของรายการเดียวกัน (C8 ปฏิเสธ) ถ้าผิด (ต้องการ fallback ไปแคมเปญถัดไปที่มีงบ): เปลี่ยนใน C8 ให้ลองแคมเปญถัดไป ไม่แก้ schema ถ้าผิด (ต้องการซ้อน): ถอด unique ของ `t_campaign_discount` และกำหนดลำดับ (เสนอ: เปอร์เซ็นต์ก่อนแล้วจำนวนเงิน บนราคาที่เหลือ) ใน `sales/01` และ `sales/02`
- **C4 [Tommy ตัดสิน] สูตรต่อรายการ** `PERCENTAGE`: `ROUND(price × quantity × discount_value / 100, 2)` (ปัดครึ่งขึ้นที่ 2 ตำแหน่ง ระดับรายการ ไม่ใช่ระดับออเดอร์) `FIXED_AMOUNT`: `discount_value × quantity` (ต่อหน่วย) แล้วใช้เพดาน C5 `t_order_item.discount` คือผลนี้ `t_order.total_discount` คือผลรวมของ `discount` ทุกรายการของออเดอร์นั้น (จึงตรง `ck_t_order_total_amount_sum` เสมอ) `price` และ `total_price` ของรายการไม่เปลี่ยน (R40) ค่าส่งไม่ถูกลด ถ้าผิด (จำนวนเงินต่อออเดอร์ ไม่ใช่ต่อหน่วย): ต้องเพิ่มกติกาแบ่งส่วนลดเข้ารายการ
- **C5 [ขอเจ้าของงานตอบ] เพดานส่วนลด: ไม่ขายต่ำกว่าต้นทุน** `discount` ของรายการไม่เกิน `(selling_price - cost_price) × quantity` ของ lot ที่ล็อกไว้ (ส่วนต่างราคาขายกับต้นทุน เท่ากับ `gross_margin × quantity` แต่คำนวณจากราคาโดยตรงเพื่อไม่พึ่ง margin ที่เป็น null ได้) ส่วนที่เกินเพดานถูกตัดทิ้ง ไม่ใช่ error เหตุผล: ต่อจากกฎห้ามขายต่ำกว่าต้นทุนที่เจ้าของงานอนุมัติแล้ว (R48) และทำให้ `gross_profit` หลังลดไม่ติดลบตาม `CHECK` เดิม ถ้าผิด (ยอมขาดทุนเพื่อโปรโมชัน): ถอดเพดาน และต้องแก้ `ck_t_order_item gross_profit >= 0` ใน sales (ของที่ส่งมอบแล้ว)
- **C6 [ขอเจ้าของงานตอบ] ใครรับภาระส่วนลดในกำไร: งบของแคมเปญ (แพลตฟอร์ม) ร้านได้ราคาเต็ม** สูตรต่อรายการ: `shop_profit = share_margin × quantity` (ไม่เปลี่ยน), `platform_profit = platform_margin × quantity - discount` (ติดลบได้ ตาราง order item ไม่ห้ามเพราะไม่มี check), `gross_profit = gross_margin × quantity - discount` (ผลรวมของสองตัวแรกเท่าเดิม) เหตุผล: งบเป็นของแพลตฟอร์ม (C1) และร้านไม่ควรเสียรายได้เพราะแคมเปญที่ตัวเองไม่ได้สร้าง ผลต่อที่ร้านเห็น: `sales/04` แสดง `grossProfit` และ `shopProfit` ให้ร้าน หลัง C6 `grossProfit` ที่ร้านเห็นลดตามส่วนลดที่แพลตฟอร์มออก และ `platformProfit` ที่ซ่อนอยู่ยังคำนวณกลับได้ (`gross - shop`) เหมือนก่อนมีแคมเปญ ดูทางเลือกใน E2 ถ้าผิด (หักจากร้าน): `shop_profit` ลดแทน แก้เฉพาะสูตรใน `sales/02` ถ้าแบ่งกัน: ต้องมีอัตราส่วนที่แคมเปญ (คอลัมน์ใหม่)
- **C7 [ขอเจ้าของงานตอบ] กันงบตอนสร้างออเดอร์ คืนที่ 3 จุดที่คืนสต็อก** กันในธุรกรรมเดียวกับการตัดสต็อกของ `sales/02` (R38) คืนเมื่อ: ยกเลิกออเดอร์รวมตัวตั้งเวลา (`sales/05`), คืนเงินเต็มจำนวน (`payment/05`), webhook `charge.refunded` ที่ payment `COMPLETED` → `REFUNDED` (`payment/02`) ไม่คืนเมื่อ payment ล้มเหลว (ออเดอร์ยังถืองบจนหมดเวลา) และไม่คืนกรณีเงินเข้าหลังออเดอร์ถูกยกเลิกไปแล้ว (R57: งบคืนไปตอนยกเลิกแล้ว) เมื่อ shipping ถูกยกเลิกหรือตีกลับจนออเดอร์กลับเป็น `PAYMENT_CONFIRMED` (S9) งบยังถือไว้ และคืนเมื่อออเดอร์ถูกคืนเงิน ถ้าผิด (ตัดตอนจ่ายเงิน): ย้ายการตัดงบไป webhook และยอมให้งบเกินได้ (เหมือนยอมให้ขายสต็อกเกิน)
- **C8 [ขอเจ้าของงานตอบ] งบไม่พอ: ปฏิเสธ ไม่ลดราคาเงียบ ๆ** ถ้างบคงเหลือไม่พอสำหรับส่วนลดของออเดอร์ checkout preview แสดงเป็นปัญหา (`DISCOUNT_BUDGET_EXHAUSTED` พร้อมรายการ `cartId` ของรายการที่ใช้แคมเปญนั้น) และ `sales/02` ตอบ 409 (E10007) พร้อมเหตุผลเดียวกัน rollback ทั้งหมด ลูกค้าดู preview ใหม่ได้ราคาที่ไม่มีแคมเปญนั้น เหตุผล: ลูกค้าเห็นราคาที่ preview ไม่ควรถูกเก็บราคาสูงกว่านั้นโดยไม่รู้ตัว ใช้รหัส E10007 เดิม (สต็อกไม่พอหรือไม่เปิดขาย) โดยไม่สร้างรหัสใหม่ ถ้าผิด (สั่งต่อโดยไม่มีส่วนลด): ออเดอร์ถูกสร้างที่ราคาเต็มทันที ลูกค้าอาจเห็นราคาที่ต่างจาก preview
- **C9 [Tommy ตัดสิน] รูปแบบกันงบและลำดับล็อก** กันงบด้วยคำสั่งเดียว `UPDATE campaign.m_campaign_budget SET remaining = remaining - n WHERE id = ... AND remaining >= n AND row_status = 'ACTIVE'` ได้ 0 แถว = งบไม่พอ (C8) แล้ว `INSERT` ledger ชนิด `RESERVE` (`usage` = n, `remaining` = ยอดคงเหลือของงบหลังรายการนี้, `order_id`, `reference` = รายการและส่วนลดต่อรายการ) การคืนคือ `UPDATE ... SET remaining = remaining + n` และ `INSERT` ledger ชนิด `RELEASE` ด้วย `usage` = n ตัวเดียวกับ `RESERVE` ของออเดอร์นั้น (ทั้งสองชนิดเก็บ `usage` เป็นจำนวนบวก ทิศทางอยู่ที่ `entry_type`) และ `remaining` = ยอดคงเหลือของงบหลังรายการนี้ ledger ไม่ลบไม่แก้ `UNIQUE (campaign_budget_id, order_id, entry_type)` กันคืนซ้ำ และการคืนต้องมี `RESERVE` ของออเดอร์นั้นก่อน (ตรวจใน SQL) ค่าคงที่ที่ตัวตรวจจะตรวจ: `budget - remaining = ผลรวม RESERVE - ผลรวม RELEASE` ลำดับล็อก (ต่อ R72): แถวออเดอร์ → lot (เรียงตาม `id`) → งบ (เรียงตาม `id`) ทุกเส้น สร้างออเดอร์ใหม่ยังไม่มีใครเห็นแถวออเดอร์ ถ้าผิด: ไม่มีผลต่อ schema นอกจากถอด `remaining`
- **C10 [Tommy ตัดสิน] หนึ่งแคมเปญหนึ่งงบที่ใช้อยู่ และแก้งบได้** ตารางยังเป็นหนึ่งต่อหลายเพื่อเพิ่มงบเสริมทีหลัง แก้ `budget` ได้เสมอเมื่อเพิ่ม และลดได้ไม่ต่ำกว่ายอดที่ใช้ไป (`budget - remaining`) ต่ำกว่านั้น 409 (E10006) `remaining` ปรับตามส่วนต่าง การแก้งบไม่เขียน ledger (บันทึกด้วย `updated_by`, `updated_at`) ถ้าผิด (หลายงบต่อแคมเปญ): ต้องกำหนดลำดับว่าตัดงบก้อนไหนก่อน
- **C11 [Tommy ตัดสิน] การเปลี่ยน schema ตามหัวข้อ 3** ถ้าผิด: ถอดคอลัมน์หรือ constraint ที่เพิ่มได้โดยไม่กระทบตารางอื่น
- **C12 [Tommy ตัดสิน] สิทธิ์และสถานะที่ให้ส่วนลด** ใช้ query สิทธิ์ชุดเดิม (Check platform administrator) เส้นเขียนไม่ใช่ `PLATFORM_ADMIN` ตอบ 403 (E10009) แคมเปญที่ `row_status` เป็น `INACTIVE`, `LOCKED`, `ARCHIVED` หรือ `DELETED` ไม่ให้ส่วนลดกับออเดอร์ใหม่ และไม่กระทบออเดอร์ที่สร้างไปแล้ว (ส่วนลดเก็บที่รายการแล้ว) `DELETED` เป็นสุดทาง ตามข้อตกลงของ upsert แถวลูกที่ไม่ ACTIVE ไม่นับ ถ้าผิด: ปรับเงื่อนไข `row_status` ใน query
- **C13 [ขอเจ้าของงานตอบ] กติกาลบ** (1) ลบแคมเปญที่เคยมี ledger (ใช้งบแล้ว) ไม่ได้ 409 (E10006) ให้ archive แทน ลบแคมเปญที่ไม่มี ledger ได้ (soft) พร้อมแถวลูกทั้งหมด (2) ลบร้าน, ลบสินค้า, ลบหมวดสินค้า ถูกห้ามด้วย 409 (E10006) เมื่อยังผูกกับแคมเปญที่ไม่ `DELETED` และยัง `end_at > now` ผูกกับแคมเปญที่จบแล้วหรือถูกลบแล้วลบได้ (แถวผูกเก่าเป็นประวัติ) archive ร้านทำได้เสมอ (3) lot ไม่มีกติกาเพิ่ม เพราะแคมเปญไม่ผูก lot (4) แก้หรือลบส่วนลดและงบระหว่างแคมเปญทำงานได้ มีผลกับออเดอร์ใหม่เท่านั้น เหตุผล: ตามแนวของโปรเจกต์ที่ห้ามลบของที่ถูกใช้อยู่ (shop type, lot ที่เปิดขาย) ถ้าผิด (ลบร้านแล้วปลดผูกให้อัตโนมัติ): เปลี่ยน 409 เป็น soft delete แถวผูกในธุรกรรมเดียวกัน ไม่กระทบ schema
- **C14 [Tommy ตัดสิน] ไม่มีกติกายอดชำระขั้นต่ำในแคมเปญ** ขั้นต่ำ 10.00 ของ payment (R65) ตรวจกับ `amount` ซึ่งรวมค่าส่ง (R67 ต่ำสุดตอนนี้ 40.00) และส่วนลดไม่เกินราคาสินค้า (C5) จึง `amount >= shippingFee` เสมอ ขั้นต่ำชนไม่ได้ และ `sales/01`, `sales/02` ไม่ต้องมีกติกานี้ (ตรวจตามข้อสังเกตของ Josh ในประตู 1 ซึ่งแก้ข้อความเดิมของผมที่เทียบยอดโดยไม่รวมค่าส่ง) ถ้าผิด (ค่าส่งฟรีหรือค่าส่งต่ำกว่าขั้นต่ำในอนาคต): เพิ่มกติกาตอนนั้น
- **C15 [Tommy ตัดสิน] bizCode ใช้ชุดเดิม** E10001 คำขอผิด (เปอร์เซ็นต์เกิน 100, ช่วงเวลาผิด, ส่ง id ซ้ำ) · E10003 ชื่อแคมเปญซ้ำ, หมายเลขซ้ำใน unique ของลูก · E10004 ไม่พบแคมเปญ · E10005 ไม่พบร้าน สินค้า หรือหมวดที่อ้างถึง · E10006 ลบหรือแก้ไม่ได้ (ใช้งบแล้ว, ลดงบต่ำกว่าที่ใช้, ถูกใช้อยู่) · E10007 งบไม่พอที่ checkout (C8) · E10009 สิทธิ์ ถ้าผิด: ถามก่อนสร้างรหัสใหม่

- **C22 [Tommy ตัดสิน] `09-campaign.test.sql` test 1 และ 2 เดิมถูกแก้ให้ส่ง `remaining`** เพราะคอลัมน์ใหม่เป็น NOT NULL ไม่มี default (default อ้างคอลัมน์อื่นไม่ได้) และเพิ่มข้อทดสอบที่ INACTIVE ยังถือที่ของงบเพราะ mutation ชุดแรกหลุด ถ้าผิด: ไม่มี
- **ข้อจำกัดของเครื่องมือ:** `audit_all.py` ไม่ตรวจชื่อคอลัมน์ที่ไม่มี alias ใน `WHERE` ของ `UPDATE` (เช่น `AND remaining >= ...` ใน `sales/02`) mutation ที่พิมพ์ชื่อผิดตรงนั้นหลุดจาก audit และถูกตัวตรวจ `campaign-spec` จับด้วย needle แทน

## 5. คำถามธุรกิจ (ชุดเดียว เรียงตามความสำคัญ)

1. **ใครสร้างแคมเปญ** (C1): เสนอแพลตฟอร์มเท่านั้น ร้านเข้าร่วมเมื่อแพลตฟอร์มเพิ่ม ถ้าผิด: ต้องมีเจ้าของแคมเปญและงบของร้าน
2. **ใครรับภาระส่วนลดและเพดาน** (C5, C6): เสนอแพลตฟอร์มรับจากงบ ร้านได้ราคาเต็ม และส่วนลดไม่เกินกำไรขั้นต้นของรายการ (ไม่ขายต่ำกว่าต้นทุน ต่อจาก R48) ถ้าผิด: สูตรกำไรใน sales/02 หรือถอด check
3. **งบ: กันเมื่อไรและหมดแล้วทำอย่างไร** (C7, C8): เสนอกันตอนสร้างออเดอร์ คืนเมื่อยกเลิก หมดเวลา หรือคืนเงิน และเมื่องบไม่พอให้ปฏิเสธ (409) ไม่ลดราคาเงียบ ๆ ถ้าผิด: ตัดตอนจ่ายเงินและยอมให้งบเกิน หรือสั่งต่อที่ราคาเต็ม
4. **ส่วนลดซ้อนและสูตร** (C3, C4): เสนอไม่ซ้อนข้ามแคมเปญ (เลือกที่ลดมากสุด) หนึ่งแคมเปญหนึ่งส่วนลด และ `FIXED_AMOUNT` คิดต่อหน่วย ถ้าผิด: กำหนดลำดับซ้อนหรือแบ่งส่วนลดต่อออเดอร์
5. **ขอบเขตของแคมเปญ** (C2): เสนอว่าแคมเปญที่ไม่ระบุร้านหรือสินค้า = ใช้กับทั้งหมด และเลือกหมวดหมายถึงหมวดนั้นเท่านั้น ไม่รวมหมวดลูก ถ้าผิด: กลับเงื่อนไขหรือเพิ่มคอลัมน์ scope
6. **กติกาลบ** (C13): เสนอห้ามลบร้าน สินค้า หมวด ที่ผูกกับแคมเปญที่ยังไม่จบ ห้ามลบแคมเปญที่ใช้งบแล้ว (ให้ archive) ถ้าผิด: ปลดผูกให้อัตโนมัติแทน
7. **ที่ที่ลูกค้าเห็นส่วนลด** (ไม่ใช่เป้าหมาย): เสนอเห็นเฉพาะที่ checkout และในออเดอร์ ไม่แสดงราคาลดที่หน้าสินค้าและตะกร้า ถ้าผิด: ต้องเพิ่มการคำนวณในหน้าสินค้า (`shop/04`, `shop/14`) และตะกร้า (`cart/03`) ซึ่งเป็นงานที่ส่งแล้วอีกหลายเส้น
