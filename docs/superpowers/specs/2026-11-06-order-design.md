# สั่งซื้อ (order) — WP1

วันที่: 2026-11-06 · สถานะ: ทำตามคำสั่งของเจ้าของงาน ("เริ่มทำ sales หรือ order ได้เลย") การตัดสินใจระหว่างทางรอตรวจ (หัวข้อสุดท้าย)

ต่อจาก [ตะกร้าสินค้า](2026-11-06-cart-design.md) และ [แผน API](../plans/2026-11-06-api-roadmap.md) (WP1) ตะกร้าอ่านราคาจาก lot ที่เปิดขาย ออเดอร์คือจุดที่ราคาถูกล็อกและสต็อกถูกตัด

## เป้าหมาย

- ลูกค้าดูตัวอย่างการสั่งซื้อ (checkout preview) แล้วสร้างออเดอร์จากตะกร้า หนึ่งออเดอร์ต่อหนึ่งร้าน
- ล็อกราคาและ lot ของแต่ละรายการ ณ ตอนสร้างออเดอร์ และตัดสต็อกจาก lot นั้น
- ลูกค้าและร้านดูออเดอร์ของตัวเอง ยกเลิกออเดอร์ที่ยังไม่จ่ายเงินได้ และสต็อกกลับเข้า lot

## ไม่ใช่เป้าหมาย

- การชำระเงิน การคืนเงิน (WP2) การจัดส่ง (WP3) ส่วนลดจากแคมเปญ (WP7) ภาษีและค่าส่งที่คิดจริง
- การแก้ออเดอร์หลังสร้าง (เปลี่ยนที่อยู่ เปลี่ยนจำนวน) ลูกค้ายกเลิกแล้วสั่งใหม่
- งานตัวตั้งเวลา (job) ที่ยกเลิกออเดอร์หมดเวลา spec เขียนแค่กติกา ไม่ใช่ API

## ผลงาน

- Schema: `sales.t_order` เพิ่ม `ship_*` (สำเนาที่อยู่จัดส่ง) และ `expires_at`, `CHECK ck_t_order_total_amount_sum`, `address_id` เป็น `ON DELETE RESTRICT` (migration `06`, schema doc, README, ER diagram หน้า 6 และ 8, แบบทดสอบ `db/tests/06-sales.test.sql` test 4–6)
- Spec ใน `e-commerce/doc/api/sales/`: `01-inquiry-checkout`, `02-create-order`, `03-inquiry-order`, `04-inquiry-shop-order`, `05-cancel-order`
- ตัวตรวจ `check_docs.py order-spec`

## การตัดสินใจระหว่างทาง (รอเจ้าของงานตรวจ)

- R38 ตัดสต็อกตอนสร้างออเดอร์ ไม่รอจ่ายเงิน (เจ้าของงานอนุมัติข้อเสนอแล้ว) ออเดอร์เกิดในสถานะ `WAIT_PAYMENT` และถือสต็อกจนถึง `expires_at` (ค่า config, เสนอ 30 นาที) ถ้าไม่จ่ายภายในเวลา ตัวตั้งเวลายกเลิกออเดอร์และคืนสต็อกเหมือนการยกเลิกปกติ ถ้าผิด (อยากตัดตอนจ่าย): ต้องเอา `expires_at` ออกและยอมให้ขายเกิน
- R39 หนึ่ง checkout สร้างหนึ่งออเดอร์ต่อร้าน (เจ้าของงานอนุมัติแล้ว) ทุกออเดอร์สำเร็จหรือล้มทั้งคำขอ (transaction เดียว) การจ่ายเงินรวมหรือแยกตามร้านเป็นเรื่องของ WP2 ถ้าผิด: ต้องมีตาราง order group
- R40 ราคาล็อกจาก lot ที่เปิดขาย ณ ตอนสร้างออเดอร์ (เจ้าของงานอนุมัติแล้ว) `t_order_item.price` คือราคานั้น `lot_id` คือ lot นั้น กำไรของรายการ (`gross_profit`, `shop_profit`, `platform_profit`) คือ margin ของ lot คูณจำนวน
- R41 ส่วนลด ภาษี และค่าส่งเป็น 0 ทุกออเดอร์จนกว่า WP7 และกติกาค่าส่งจะมี (ผมตัดสินเอง เจ้าของงานยังไม่ตอบ) schema บังคับสูตร `total_amount = total_price - total_discount + total_tax + total_shipping` ไว้แล้ว จึงเสียบการคำนวณทีหลังได้โดยไม่แก้ schema ถ้าผิด: ต้องเพิ่มขั้นตอนคำนวณใน spec 01 และ 02
- R42 ออเดอร์เก็บสำเนาที่อยู่จัดส่ง ณ ตอนสั่ง (คอลัมน์ `ship_*` ค่าเข้ารหัสแบบเดียวกับที่อยู่ของผู้ใช้) เพื่อไม่ให้ที่อยู่เก่าเปลี่ยนตามเมื่อผู้ใช้แก้ที่อยู่ (ผมตัดสินเอง) `address_id` ยังเก็บไว้อ้างอิง และเปลี่ยนเป็น `RESTRICT` เพื่อไม่ให้ลบที่อยู่จริงแล้วออเดอร์หาย ถ้าผิด: ลบคอลัมน์ `ship_*` ได้โดยไม่กระทบอย่างอื่น
- R43 ลำดับสถานะ: `WAIT_PAYMENT` → (WP2) `PAYMENT_CONFIRMED` → (WP3) `PROCESSING` → `COMPLETED`, ยกเลิกได้เฉพาะ `WAIT_PAYMENT` ในงานนี้ (`CANCELLED`) หลังจ่ายแล้วต้องผ่านการคืนเงินของ WP2 (`REFUNDED`) สถานะ `PENDING` ไม่ถูกใช้ใน WP1 (ออเดอร์สร้างตรงเป็น `WAIT_PAYMENT`) คงไว้ใน schema เพราะเป็นของที่ส่งแล้ว
- R44 checkout เลือกบรรทัดได้ด้วย `cartIds` ไม่ส่ง = ทุกบรรทัด ACTIVE ในตะกร้า ถ้ามีบรรทัดที่ไม่ AVAILABLE ในที่เลือก (หมด สต็อกไม่พอ ไม่เปิดขาย ร้านปิด) ตอบ 409 (E10007) พร้อมรายการปัญหา และไม่สร้างอะไร หน้า preview คืนปัญหาเดียวกันโดยไม่เขียนข้อมูล ถ้าผิด (อยากให้ข้ามบรรทัดเสียแล้วสั่งส่วนที่เหลือ): เปลี่ยนเป็นกฎข้าม
- R45 สต็อกถูกตัดด้วย UPDATE ที่มีเงื่อนไข `quantity >= n` และ `is_on_sale` ในคำสั่งเดียว ถ้าได้ 0 แถว (คนอื่นซื้อไปก่อน) ตอบ 409 (E10007) และ rollback ทั้งหมด lot ที่หมดสต็อกไม่เปลี่ยน lot เอง (กฎเดิมของ lot) ถ้าผิด: ไม่มี
- R46 ยกเลิก: เจ้าของออเดอร์ สมาชิกของร้านนั้น หรือ `PLATFORM_ADMIN` ยกเลิกได้ ผู้อื่นเห็นเป็นไม่พบ (404 E10004) สถานะที่ไม่ใช่ `WAIT_PAYMENT` ตอบ 409 (E10006) สต็อกกลับเข้า lot เดิมของรายการ (`lot_id`) แม้ lot นั้นไม่ได้เปิดขายแล้ว ถ้าผิด: ไม่มี
- R47 ร้านเห็นออเดอร์ของร้านตัวเองเท่านั้น (สมาชิก ACTIVE ของร้านหรือ `PLATFORM_ADMIN`, ไม่ใช่ → 403 E10009) ร้านเห็น `grossProfit` และ `shopProfit` แต่ `platformProfit` เห็นเฉพาะ `PLATFORM_ADMIN` (คืน null สำหรับร้าน) เพราะสอดคล้องกับกติกาซ่อน margin ของแพลตฟอร์มที่เจ้าของงานอนุมัติแล้ว ถ้าผิด: ปรับสิทธิ์ใน spec 04
- R48 ขายต่ำกว่าต้นทุนไม่ได้ (เจ้าของงานอนุมัติให้ห้ามที่ lot) `t_shop_product_sku_lot` มี `CHECK ck_t_shop_product_sku_lot_price_not_below_cost (selling_price >= cost_price)` และ spec lot (`shop/01`, `shop/02`) ตอบ 400 เมื่อราคาขายต่ำกว่าต้นทุน จึงไม่มี lot ที่ทำให้ `t_order_item.gross_profit` ติดลบ และ spec สั่งซื้อไม่ต้องมีกรณีนี้ ถ้าผิด (อยากขายขาดทุนได้เช่นเคลียร์สต็อก): ต้องถอด CHECK ทั้งสองที่และปรับ `gross_profit` ให้ติดลบได้
- R49 รหัสออเดอร์ (`code`) สร้างโดยระบบรูปแบบ `ORD-YYYYMMDD-NNNNNN` ไม่ซ้ำ (unique ใน schema ตามเดิม ซ้ำให้สร้างใหม่) ไม่ใช่ฟิลด์ของคำขอ
- R50 bizCode: ใช้ E10007 กับสต็อกและการเปิดขาย (ตามตะกร้า) E10006 กับยกเลิกไม่ได้เพราะสถานะ E10009 กับสิทธิ์ ไม่มีรหัสใหม่
