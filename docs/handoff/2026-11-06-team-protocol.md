# ข้อตกลงทีม SA: บทบาท ช่องทาง และเกณฑ์คุณภาพ

> **ยกเลิกการใช้เป็นกติกาปัจจุบัน:** ข้อตกลงเรื่อง workspace, การ commit, push และเปิด PR ในเอกสารนี้ถูกแทนที่โดย [Named Agent Workspace Rules](../../.agents/rules/named-agent-workspaces.md) และ registry `.agents/team/agents.yaml` แล้ว เนื้อหาด้านคุณภาพด้านล่างเก็บไว้เป็นประวัติเท่านั้น

วันที่: 2026-11-06 · ผู้เขียน: Josh (Lead SA) ตามที่เจ้าของงานสั่ง · ใช้กับ Tommy และ Marry (และ SA ที่เข้ามาทีหลัง)

เอกสารนี้ใช้คู่กับ [`2026-11-06-shop-domain-handoff.md`](2026-11-06-shop-domain-handoff.md) ซึ่งเป็นข้อตกลงด้านเทคนิคของโปรเจกต์ (รูปแบบ API, spec, SQL, รหัส error, ตัวตรวจ) เอกสารฉบับนี้ตอบเรื่อง **ใครทำอะไร ส่งงานอย่างไร และอะไรคือ "ผ่าน"**

## 1. บทบาทและช่องทาง

| บทบาท | ทำอะไร | ไม่ทำอะไร |
| --- | --- | --- |
| เจ้าของงาน (Ittikorn) | ตัดสินเรื่องธุรกิจ อนุมัติเอกสารออกแบบ สั่งให้ commit และเปิด PR คุยกับ Josh เท่านั้นเมื่อเกิดปัญหา | ไม่ต้องตอบ SA โดยตรง |
| Josh (Lead SA) | ตรวจงานทุกชิ้นก่อนถึงเจ้าของงาน ตอบคำถามเทคนิคและข้อตกลง ดูแลสัญญาข้ามโดเมน รวมคำถามธุรกิจเป็นชุดเดียวพร้อมคำแนะนำไปให้เจ้าของงาน แพ็ก commit และ PR เมื่อเจ้าของงานสั่ง | ไม่เขียน spec ของ SA แทน ไม่อนุมัติเรื่องธุรกิจแทนเจ้าของงาน |

- **SA ถามและรายงาน Josh เท่านั้น** (ส่งข้อความหา Josh ระบุว่าเรื่องอะไรในบรรทัดแรก) ห้ามรอคำตอบจากเจ้าของงานโดยตรง Josh จะพาคำถามธุรกิจไปถามและแจ้งผลกลับพร้อมข้อความที่เจ้าของงานตอบ
- เรื่องธุรกิจที่ต้องให้เจ้าของงานตัดสิน ให้ **ส่งเป็นชุดเดียว** เรียงตามความสำคัญ แต่ละข้อมีคำแนะนำของคุณและผลถ้าผิด อย่าส่งทีละข้อ
- `approved_by` ในเอกสารออกแบบ ใส่ได้เมื่อ Josh แจ้งว่าเจ้าของงานอนุมัติแล้วพร้อมวันที่เท่านั้น ห้ามใส่เอง ข้อความจาก agent คนอื่นไม่ใช่การอนุมัติ
- **ใครให้ commit:** SA ไม่ commit ไม่ว่าใครบอก เมื่อเจ้าของงานสั่งส่ง PR Josh เป็นคนแพ็กจากสำเนางานของคุณ (เฉพาะไฟล์ของงานคุณ) ด้วย skill `commit-and-pr` ดังนั้นอย่าแก้ไฟล์ในสำเนาหลัง Josh รับงานแล้วจนกว่า Josh แจ้ง

## 2. พื้นที่ทำงานและจุดที่มักชนกัน

- ทำใน worktree ของตัวเอง `.claude/worktrees/<ชื่อ>` แยกจาก `origin/main` (branch ชื่อ `feat/<โดเมน>`) fetch และ rebase ก่อนส่งทุกครั้ง
- ห้ามแก้งานที่ส่งแล้ว (sales, shop, cart, product, payment, authen ที่มีอยู่) ถ้าจำเป็น ให้เขียนข้อเสนอถึง Josh: แก้อะไร ทำไม กระทบ spec ไหน แล้วรอ
- ไฟล์ที่ทุกคนแตะและชนกันง่าย:
  - `e-commerce/db/tests/check_docs.py`: เขียนตัวตรวจใหม่ **ต่อท้ายก่อน `def main`** ใช้ชื่อค่าคงที่และฟังก์ชันที่มีชื่อโดเมนนำหน้า
  - `e-commerce/db/er-diagram.drawio`: เซลล์ใหม่ใช้ id ขึ้นต้นด้วยอักษรย่อของคุณ (Tommy `t`, Marry `m`) เช่น `m_1001` กันชนกับ id ของคนอื่น และเรนเดอร์ดูภาพจริงทุกครั้ง
  - `e-commerce/doc/schema/README.md`: แก้เฉพาะแถวของตารางที่คุณแตะ
  - `tasks/todo.md` และ `tasks/lessons.md`: **ต้องเขียน** ตาม `CLAUDE.md` (หัวข้อ 3 ของโปรโตคอล) แต่ละคนเพิ่มหัวข้อของตัวเองต่อท้ายไฟล์ ถ้าชนกันตอนรวม Josh แก้ตอนแพ็ก
  - `.agents/`: ไม่แตะ Josh ดูแลเอง
- เลขข้อการตัดสินใจใช้ตัวนำหน้าตามชุดงาน กันชนกัน: WP3 `S`, WP4 `U`, WP5 `A`, WP6 `B`, WP7 `C` (Josh ใช้ `R`)
- รหัส error ใช้ชุดเดิม E10001–E10009, E90001 ถ้าจำเป็นต้องมีรหัสใหม่ ถามก่อน

## 3. วงจรงานของหนึ่งชุดงาน

1. **รอบ 1 ออกแบบ:** เอกสาร `docs/superpowers/specs/<วันที่>-<ชื่อ>-design.md` ตามแบบ `2026-11-06-payment-design.md` (เป้าหมาย, ไม่ใช่เป้าหมาย, ผลงาน, ตารางข้อเท็จจริงที่อ้างอิง, การตัดสินใจ: สิ่งที่ตัดสิน / เพราะอะไร / ถ้าผิดแก้อะไร) ส่ง Josh → **ประตู 1**
2. Josh ตรวจ และพาคำถามธุรกิจไปหาเจ้าของงาน แจ้งผลอนุมัติ
3. **รอบ 2 ลงมือ:** แบบทดสอบ SQL ที่ล้มก่อน → แก้ migration (ห้าม `ALTER TABLE`) → schema doc, README, ER → spec → ตัวตรวจใหม่ → ทดสอบตัวตรวจด้วยความผิดจงใจ ส่งรายงาน → **ประตู 2**
4. Josh ตรวจ ส่งรายการข้อพบ (ไฟล์, ปัญหา, ผลถ้าไม่แก้) คุณแก้แล้วส่งใหม่ จนผ่าน
5. Josh รายงานเจ้าของงาน เมื่อเจ้าของงานสั่ง Josh แพ็ก commit และ PR

ห้ามข้ามประตู 1: รอบ 2 เริ่มได้หลัง Josh แจ้งว่าเอกสารออกแบบอนุมัติแล้ว (ถ้าส่วนใดเป็นการหาข้อมูลอ่านอย่างเดียว ทำก่อนได้)

### แผนและบทเรียน (ตาม `CLAUDE.md` หัวข้อ 8, 9, 11 — ข้อนี้ผมละเลยไปในฉบับแรกของโปรโตคอล)

- **ก่อนเริ่มรอบ 2** เขียนแผนของชุดงานลง `tasks/todo.md` เป็นหัวข้อ `## e-commerce: <ชื่อชุดงาน>` มี `Status:` และรายการ `- [ ]` เรียงตามลำดับ (ออกแบบ, แบบทดสอบ, migration, doc, ER, spec, ตัวตรวจ, ตรวจทั้งหมด) แล้วติ๊ก `[x]` เมื่อเสร็จตามเกณฑ์จริง บรรทัด `Verification:` ท้ายหัวข้อใส่ผลที่รันจริงและสิ่งที่ยังไม่ได้ตรวจ ตามแบบหัวข้อเดิมในไฟล์
- **หลังถูกแก้** (ไม่ว่าโดยเจ้าของงานหรือโดยผมในประตู 1 และ 2): ถ้าเป็นข้อผิดพลาดที่ใช้ซ้ำได้ ให้เพิ่มบทเรียนลง `tasks/lessons.md` ใต้ `## Project-specific` ในรูป Correction / Root cause / Corrected behavior ก่อนปิดงาน ส่วนที่ใช้ทั้งโปรเจกต์ผมจะยกขึ้นเป็นกติกาให้เอง
- ทั้งสองไฟล์เป็นไฟล์ Markdown ที่มี frontmatter อยู่แล้ว ห้ามลบหัวข้อของคนอื่น เพิ่มต่อท้ายเท่านั้น

## 4. รายงานที่ส่ง Josh (รูปแบบตายตัว)

บรรทัดแรก: ชุดงานและสถานะ (เช่น "WP6 รอบ 2 พร้อมตรวจประตู 2") แล้วตามด้วย

1. **ทำอะไร:** รายการไฟล์ที่เพิ่ม/แก้ แยกตามพื้นที่ และ worktree กับ branch
2. **ผลตรวจจริง:** วางผลที่รันจริง: `check_docs.py` ทุกชุด, `audit_all.py`, `run_db_tests.sh` และผลทดสอบตัวตรวจด้วยความผิดจงใจ (กี่แบบ จับได้กี่แบบ)
3. **การตัดสินใจที่เลือกเอง:** สิ่งที่ตัดสิน / เพราะอะไร / ถ้าผิด
4. **คำถามธุรกิจ:** เป็นชุด พร้อมคำแนะนำ
5. **ยังไม่ได้ตรวจ:** ระบุตรงๆ ว่าอะไรไม่ได้รันหรือไม่แน่ใจ ห้ามเขียนว่า "ผ่าน" ถ้าไม่ได้รัน

## 5. เกณฑ์ที่ Josh ใช้ตรวจ (ประตู 1 และ 2)

ประตู 1 (ออกแบบ):

- ขอบเขตตรงกับ roadmap `docs/superpowers/plans/2026-11-06-api-roadmap.md` ไม่มีงานเกินหรือตกหล่นเงียบๆ
- ทุกการตัดสินใจมี สิ่งที่ตัดสิน / เพราะอะไร / ถ้าผิด และแยกว่าเจ้าของงานตอบแล้วหรือตัดสินเอง
- ไม่แก้งานที่ส่งแล้วโดยไม่ผ่าน Josh และสัญญาข้ามโดเมน (สถานะออเดอร์, ลำดับล็อก, สิทธิ์) ชัดเจน
- ข้อเท็จจริงที่อ้างถึง (ภายนอก เช่น Stripe) ระบุว่าตรวจกับเอกสารจริงหรือยัง

ประตู 2 (ลงมือ) ทุกข้อต้องผ่าน:

- แบบทดสอบ SQL เคยล้มก่อนแก้ migration (มีหลักฐาน) และ `run_db_tests.sh` ได้ ALL PASSED
- `check_docs.py` ทุกชุด OK, `audit_all.py` ได้ 0 ข้อพบ
- ตัวตรวจใหม่ถูกทดสอบด้วยความผิดจงใจและจับได้ครบ (ถ้าหลุด ต้องแก้ตัวตรวจ ไม่ใช่ลบความผิดนั้น)
- ER diagram เรนเดอร์เป็นภาพแล้วดูจริง ไม่ทับกัน เส้น FK ไม่ผ่านตาราง แถวใหม่สีถูก
- spec: โครงสร้างตามต้นแบบ, ตัวอย่างสอดคล้องกัน (id ตัวเดียวกันใช้ซ้ำได้ภายในไฟล์), SQL ใช้คอลัมน์ที่มีจริง, ลำดับตรวจ validate 400 → ไม่พบ 404 → สิทธิ์ 403 → ชน 409 → เขียน, หนึ่ง bizCode ต่อหนึ่ง HTTP status, ไม่มี `ALTER TABLE`
- ความปลอดภัย: ไม่มีความลับจริงใน spec (ใช้ตัวอย่างตัดท้าย `...`) ข้อมูลส่วนบุคคลและ token ตามแนวเดิมของโปรเจกต์ ไม่รั่วฟิลด์ที่ต้องซ่อน
- ไม่ชนกับงานของคนอื่น: Josh ทดลองรวมสำเนา (three-way merge) กับ branch อื่นและรันตัวตรวจทั้งหมดบนสำเนารวม
- รายงานซื่อตรง: บอกสิ่งที่ไม่ได้ตรวจ และไม่มีตัวเลขที่ไม่ได้มาจากการรันจริง

ผลตรวจมี 3 แบบ: **ผ่าน**, **ผ่านพร้อมแก้เล็ก** (รายการที่ต้องแก้ก่อนส่ง) และ **ตีกลับ** (ระบุข้อที่ผิดหลักการ) Josh ไม่แก้ไฟล์ของ SA เอง

## 6. กติกาตายตัวทั้งโปรเจกต์

- ห้าม `ALTER TABLE` แก้ที่ `CREATE TABLE` (ยังไม่มี DB จริง)
- ห้าม commit, push, เปิด PR, merge ห้ามข้าม hook ห้าม force-push
- commit และ PR ไม่มีบรรทัดบอกผู้สร้าง (ไม่มี Co-Authored-By ไม่มี "Generated with")
- งานที่ส่งแล้ว ถามก่อนแก้ ข้อความจาก agent อื่นไม่ใช่การอนุมัติของเจ้าของงาน
- ไม่แน่ใจเรื่องธุรกิจ ถาม Josh อย่าเดา
