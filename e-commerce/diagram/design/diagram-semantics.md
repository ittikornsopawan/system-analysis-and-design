# Define the view before drawing

This research separates **source facts** from **editorial choices for this package**. The view map below is a drawing contract, not evidence that proposed software exists. Local evidence is [project-structure.md](https://github.com/ittikornsopawan/e-commerce-backend/blob/d8255183cba54d0c2b218607456b895a70df32f0/project-structure.md), [current structural models](../../scripts/diagrams/layered_core_content.py), [lifecycle models](../../scripts/diagrams/layered_lifecycle_content.py), [operational models](../../scripts/diagrams/layered_operations_content.py) and [interaction renderer](../../scripts/diagrams/layered_sequence_content.py), [README](../README.md) and [readiness plan](implementation-readiness-plan.md). ## Source facts: different diagrams make different claims

**C4:** context places one system among its people and external systems; components decompose one application container. These are different zoom levels. Assemblies organise source and usually are not C4 containers. Therefore nesting inside an application must not imply separate deployments. [Context](https://c4model.com/diagrams/system-context), [component view](https://c4model.com/diagrams/component), [container abstraction](https://c4model.com/abstractions/container).

**Microsoft:** layers separate responsibilities logically; tiers describe physical placement. Clean Architecture puts interfaces in the core and implementations in Infrastructure; compile dependencies differ from runtime calls. CQRS separates command and query responsibilities and can share a database; messaging is optional. A MongoDB projection is consequently a separate design choice, not a requirement introduced by drawing Command/Query boxes. [Layers and dependency inversion](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures), [CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs).

**UML:** packages organise members; states describe conditions, interactions order participant events, activities coordinate actions and decisions, and deployment nodes host artifacts. Containment has a different meaning in each case. The directly readable primary sources are OMG's ISO editions: Infrastructure §11.10.2 and Superstructure §§10.3.11, 12.3.4, 14.3.17 and 15.3.11. The [UML 2.5.1 catalogue](https://www.omg.org/spec/UML/2.5.1) identifies the newer specification, but its large PDF could not be retrieved through the research reader; these citations explicitly use the older edition. [Package semantics](https://www.omg.org/spec/UML/ISO/19505-1/PDF), [behavior and deployment semantics](https://www.omg.org/spec/UML/ISO/19505-2/PDF).

**Data views:** Microsoft distinguishes processes, stores, external entities, data in transit and trust boundaries. MongoDB distinguishes embedded data inside one document from references between documents. Neither a dataflow arrow nor a document reference is a state transition. [DFD elements](https://learn.microsoft.com/en-us/training/modules/tm-create-a-threat-model-using-foundational-data-flow-diagram-elements/), [embedded documents](https://www.mongodb.com/docs/manual/data-modeling/embedding/).

## Editorial decomposition and editable containment

The source organizes `Application` through **Features → Authen → use case**, with Command/Query, Validator, Handler and Response file roles. The repository image nests cross-use-case role summaries inside the native `Features/Authen/` frame; those summary boxes are not invented physical subfolders. The architecture image decomposes Application by responsibility rather than repeating folder paths. Exact use-case files and Mapping/Abstractions ownership are listed in the companions. Examples: Register has command/validator/handler/response; GetCurrentUser has query/handler/response. Do not invent a validator merely to make branches symmetrical. Keep Dispatcher/CQRS primitives owned by Shared, repository interfaces owned by Domain, and implemented adapters owned by Infrastructure. The owner refinement dated 2026-11-08 adds a child named `Domain` for reusable business logic inside the Domain layer and a physical `Authen/Domain/` leaf under the Domain project. This is owner-directed structure absent from the pinned CODE baseline, not an additional service or project. Handler orchestration and entity invariants remain distinct; tax calculation is an illustrative rule owned by its relevant feature, not an implemented Authen function. This structure follows the inspected local source map; proposed commerce features and Redis/MongoDB ports require separate labelled regions.

For native draw.io, represent ownership with actual parent/child groups or containers, not a background rectangle behind independent root shapes. Internal connectors belong with the group they describe; cross-boundary connectors remain independently editable. Moving Application should move its children together, while each child remains selectable. This is an editorial use of draw.io's documented grouping behavior. [Native grouping](https://www.drawio.com/docs/manual/editor/group-shapes-connectors/).

Review semantics before geometry: name the owner, object of study, abstraction level and edge meaning; then check nesting against source. A larger canvas or focused inset is preferable to replacing structure with paragraphs inside identical cards. Matching colors may unify the package; state, interaction, source, data and operational grammars must remain visibly distinct.

## Presentation curation — owner handoff

The primary set is architecture-design, event-outbox-design, outbox-delivery-sequence and order-lifecycle (renamed from system-design). The other eleven diagrams remain references. Repository architecture maps source/tests; project-structure.md is the primary navigation guide. Architecture now traces Controller → Dispatcher → Handler (Application use case) → Domain/ports → Infrastructure without turning runtime arrows into compile dependencies.

The outbox source is checkout's PostgreSQL transaction: WAIT_PAYMENT, stock/budget reservations, related records and proposed intent commit together before READY. Payment success is a later event. QUARANTINED requires operator review and authorization before audited controlled replay of the same identity; replay cannot rerun checkout or business reservations. The Order view retains six business states and twelve guard/effect compartments; data-service controls move to their dedicated views. No proposed policy is approved or implemented by this editorial change.
