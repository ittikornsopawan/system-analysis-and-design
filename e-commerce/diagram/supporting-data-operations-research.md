# Supporting Data Operations Evidence

Researched on 2026-11-07 against official PostgreSQL, MongoDB and Google SRE sources. This note supports [MongoDB design](mongodb-design.md) and [Redis design](redis-design.md). PostgreSQL owns commerce state; MongoDB owns non-secret configuration and derived operational documents. Recommendations below are design choices, not approved schemas, implemented services or provider guarantees. Deployed database versions, hosting, capacity and recovery objectives remain unselected.

## PostgreSQL Publication and Claims

**Provider evidence:** PostgreSQL transactions make their enclosed changes atomic. `SKIP LOCKED` is explicitly suitable for competing consumers of queue-like tables, but returns an inconsistent view and is unsuitable for general business reads. Row locks are released at transaction end. [Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html), [SELECT](https://www.postgresql.org/docs/current/sql-select.html), [locking](https://www.postgresql.org/docs/current/explicit-locking.html).

**Recommended design:** commit the business mutation and immutable outbox intent in one source transaction. A worker claims a bounded eligible batch under a short SQL transaction, persists a lease owner, unique claim token and deadline, then commits before contacting MongoDB. A SQL lock alone cannot protect delivery after that commit. Acknowledgement, retry scheduling and lease renewal must condition on the same current token; a stale worker cannot acknowledge a replacement worker's claim. Use database time for lease comparisons, bounded attempts/backoff and an explicit operator quarantine path. Lease expiry permits concurrent duplicate delivery, so destination idempotency remains mandatory. These are application protocols requiring race/crash tests, not built-in PostgreSQL lease guarantees.

The downstream design must specify eligibility predicates, reclaim access paths/indexes, batch bounds, shutdown behavior and capacity backpressure. Quarantine must remain visible and replayable; dropping an exhausted event is not successful publication. Avoid claiming global event order from claim order: parallel workers can finish out of order.

## Atomic Destination Effects

**Provider evidence:** MongoDB single-document writes are atomic; multi-document transactions can cover collections within MongoDB. Standalone deployments do not support these transactions. A unique compound index enforces uniqueness of its field combination. Majority acknowledgement depends on deployment settings; a write-concern timeout does not establish that no write occurred. [Atomicity and transactions](https://www.mongodb.com/docs/manual/core/transactions/), [transaction prerequisites](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/), [unique indexes](https://www.mongodb.com/docs/manual/core/index-unique/), [write concern](https://www.mongodb.com/docs/manual/core/replica-set-write-concern/).

**Recommended design:** one MongoDB transaction inserts the immutable event/idempotency marker and conditionally updates its current projection. Commit with explicit majority write concern and verified journaling settings before acknowledging PostgreSQL. Inserting a marker first and updating the projection separately can permanently suppress a missing effect after a crash. Projection-first processing creates the converse partial result. MongoDB's transaction does not include the source acknowledgement; lost acknowledgement must cause harmless redelivery. [Journaling caveat](https://www.mongodb.com/docs/v8.0/reference/write-concern/).

Keep a canonicalization version and cryptographic payload hash with event identity. An existing identity plus identical canonical payload is a duplicate; a different hash is an integrity conflict requiring quarantine and investigation, never silent success or overwrite. This comparison is an application rule: uniqueness alone cannot establish payload equality. Resolve duplicate-key races by verifying the committed record, then retrying/reconciling as appropriate. Handle uncertain transaction outcomes through supported driver retry/commit semantics; no payment/provider side effects belong in a retriable callback. [.NET transaction API](https://www.mongodb.com/docs/drivers/csharp/current/crud/transactions/).

Current projections accept complete approved snapshots only when the incoming aggregate version is newer within the active source epoch. Older events may remain in event history while their projection update is a no-op in the same transaction. Partial patches require ordered gap handling and are outside this bounded recommendation.

## Documents, Indexes and Evolution

For the document diagram, distinguish current configuration, immutable configuration revisions, audit/integration events and current transaction projections. Proposed envelope fields include source epoch, event/aggregate identity, aggregate version, schema version, timestamps, hash and minimized payload. Do not imply that an audit event is a financial ledger or a current projection is complete history.

Candidate indexes are unique event identity `(sourceEpoch, eventId)`, unique projection identity `(sourceEpoch, aggregateType, aggregateId)`, and investigation ordering `(sourceEpoch, aggregateType, aggregateId, sourceVersion, eventId)`. Configuration needs its existing logical-identity and revision uniqueness. Actual search filters need separate evidence and explain plans; index field order and prefixes determine supported access paths. These are candidates for later modeling, not collection provisioning instructions. [Compound indexes](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-compound/).

Keep `schemaVersion`, aggregate version, configuration revision, authority epoch and Redis policy/counter epoch distinct. MongoDB documents can coexist in multiple schema versions, which changes query/index requirements. Recommend readers compatible with old and new approved shapes before writer rollout, rejecting unknown schemas and validating migrations before tightening validators. Schema flexibility is not automatic semantic compatibility. [Schema versioning](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/data-versioning/schema-versioning/), [validation behavior](https://www.mongodb.com/docs/manual/core/schema-validation/handle-invalid-documents/).

## Deployment and Observable Objectives

Show a proposed MongoDB replica set, with primary and two data-bearing secondaries across failure domains where available. MongoDB recommends this three-member form; an arbiter does not store another data copy. This topology is a resilience starting point, not measured capacity or uninterrupted availability. Keep configuration publishing and projection writing under separate credentials and resource budgets; a shared replica set does not isolate their workload. [Replica-set architecture](https://www.mongodb.com/docs/manual/core/replica-set-architecture-three-members/).

The observability diagram should connect source commit time to destination commit and serving watermark. Track oldest eligible outbox age, backlog, claim expiry, retry/quarantine counts, duplicate conflicts, projection version discrepancies, configuration age, replica health, storage growth, backup age and restore-drill results. Prefer low-cardinality labels; event identifiers belong in redacted diagnostic records.

Google SRE distinguishes freshness, coverage and correctness measurements. Recommend measuring all three: successful delivery latency alone hides omitted events. Reconcile samples against authoritative SQL and expose stale projection reads. The current five-second lag, thirty-second polling and five-minute configuration allowance are untested proposals; their measurement windows, denominators, outage treatment and alert policy require approval. No availability percentage or throughput is established here. [SLI guidance](https://sre.google/workbook/implementing-slos/), [pipeline reliability](https://sre.google/workbook/data-processing/).

## Coordinated Recovery and Retention

PostgreSQL PITR requires a suitable base backup and continuous WAL archive; ordinary logical dumps cannot supply that replay chain. MongoDB backup methods have topology-specific consistency requirements; a live `mongodump` without oplog capture need not represent one instant. Independent backups do not create a cross-store recovery point. [PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html), [MongoDB backup methods](https://www.mongodb.com/docs/manual/core/backups/), [mongodump](https://www.mongodb.com/docs/database-tools/mongodump/).

**Recommended recovery sequence:** fence old writers/relays, restore SQL to a recorded point, and quarantine MongoDB projections/events that may be ahead. A restored aggregate version can be lower than MongoDB's copy; ordinary newer-version filtering cannot repair this. Issue a new externally controlled source authority epoch, rebuild derived current projections into its namespace, reconcile, then activate that epoch for all readers/writers. Reject old epochs; revoke old worker access and isolate their namespace so a paused in-flight writer cannot contaminate the activated generation. An epoch merely restored from the same backup is insufficient fencing. This is a proposed recovery protocol, not a PostgreSQL/MongoDB feature. Preserve superseded evidence separately; never reinterpret discarded-timeline events as restored business truth. Recover MongoDB-owned configuration/history independently and validate fleet activation before protected functions resume.

Approve finite collection-specific retention, storage budgets and archive/replay horizons before production. The current no-automatic-TTL position does not authorize infinite affordable retention. Idempotency evidence must cover every permitted redelivery/replay horizon; expired history limits safe replay. TTL deletion is delayed background work, not a precise deletion deadline. [TTL behavior](https://www.mongodb.com/docs/current/core/index-ttl/).

Rebuilding current status from SQL cannot recreate deleted audit actors, intermediate transitions or lost event payloads. Restoring those requires retained authoritative evidence/backups; label gaps explicitly. Define separate acceptable data-loss windows (RPO) and restoration-time objectives (RTO) for commerce, configuration, audit and derived search, then demonstrate them through restore/replay drills including fencing and reconciliation. No numerical RPO/RTO is justified without that evidence. No runtime, load, failover or restore test was performed for this research.
